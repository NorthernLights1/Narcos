# Incident, 8 September 2026 - machine down, a month with no backup

Written the same day, from commands run on the client's PC and on dumps
restored here. Every number below was observed, not recalled.

**Outcome:** no data lost. 497 documents recovered, of which 377 existed
nowhere but that machine. Service restored the same day.

---

## 1. What the owner saw

Docker Desktop showed "An unexpected error occurred" and would not start. The
app would not open. The PC had been crashing under power cuts roughly three
times a day. The last backup was dated 8 August, a month earlier.

Last recorded activity in the system: **2026-09-05 14:26**. Sales were entered
daily right up to that afternoon, so a month of trade existed only in the live
database.

---

## 2. What went wrong

**A. Docker would not start - one config file, 124 bytes of NUL.**
`C:\Users\hp\.docker\daemon.json` was zero-filled. NTFS commits a file's size
before its contents reach disk, so a power cut leaves the file readable and
empty of meaning. Nothing was wrong with the engine, the images or the data.
The other four config files were intact. -> R98

**B. The dialog's own remedy would have destroyed the business.**
The error box offers two buttons: Quit, and *Reset to factory defaults*. Reset
deletes named volumes, and `pgdata` is a named volume. The fix presented on
screen to a worried person during an outage deletes the database. -> R98

**C. The scheduled backup did not exist.** Not broken, not misconfigured -
absent. `Get-ScheduledTask` matched only five built-in Windows tasks. The
8 August backup was taken by `deploy.ps1` during the v1.1.0 update, which is
why it is dated the same day as the tag. Nothing had ever run on a schedule.

**D. `ops\` held one file.** Only `docker-backup.ps1`. No `deploy.ps1`, no
`docker-restore.ps1`, no guide. A restore drill was impossible on that machine
even if someone had tried.

**E. Retention would have deleted the last good backup.** It counted every
directory under the backup root as a backup, including the empty folders each
crashed run leaves behind. Executed against the client's state, the old code
kept fifteen folders, thirteen empty, and deleted the only real backup while
printing success. -> R97

**F. The backup could not report its own failure.** `powershell.exe -File`
exits 0 even when the script threw, so Task Scheduler's `LastTaskResult` said
success regardless. -> R100

**G. It also depended on a working directory nobody had set.** `.env` was read
relatively, so a wrong "Start in" meant a silent failure every day. -> R99

**H. WSL2 had no memory cap.** No `.wslconfig` existed, so WSL2 took roughly
half of 8 GB and never gave it back. Docker made the machine unusable, which is
why the owner had been killing it.

**I. The Docker CLI pointed at the wrong engine.** The active context was
`default` (`npipe:////./pipe/docker_engine`) rather than `desktop-linux`
(`dockerDesktopLinuxEngine`). Even with Docker Desktop running, every
`docker compose` command failed.

**J. The image store lost its contents; volumes did not.** `postgres:16` and
the app image both had to be pulled again. Volumes survived intact.

**K. The boot chain was never completed.** `AutoAdminLogon = 0`. The machine
boots to a lock screen, so nothing starts until a person signs in. Documented
since July, never applied. -> R101, decided as D131

**L. My own shutdown advice broke the restart.** I recommended
`docker compose down` before shutting Windows down. It removes the containers,
and `restart: unless-stopped` cannot revive what does not exist. `stop` is no
better: it marks them deliberately stopped, the one case that policy refuses.
Correct answer: shut Windows down and touch nothing.

**A pattern worth naming.** C, E, F and G are the same defect wearing different
clothes: every failure in this backup system was invisible. Retention deleted
good backups while printing success. A wrong directory failed quietly every
day. The result code could not express failure. The task did not exist and
nothing said so. That is why a month went missing and nobody noticed.

---

## 3. What went right

**The volumes never lost anything.** Through repeated hard crashes, a corrupted
config, a wiped image store and a `compose down`, `narcos_pgdata` and
`narcos_media` came through every time. Data has never lived in the containers,
and containers rebuild in fifteen seconds.

**Postgres crash-safety held.** Three power cuts a day for a month, and the
database restored cleanly with no repair step.

**The 8 August backup was genuinely restorable.** Restored here into a real
`postgres:16`: no errors, 120 documents, correct dates. A month stale, but real.

**`.env` was in every backup folder.** The one recovery input not in git or the
image. Without it a bare-metal rebuild is guesswork. D13's design earned itself.

**The dump was tiny and that mattered.** 227,887 bytes. Small enough to pull
over a remote link in seconds, which is why the emergency ended in minutes
rather than by copying a multi-gigabyte disk image.

**`restart: unless-stopped` worked whenever containers existed.** Every failure
to come back traced to containers being removed, never to the policy.

**Once created, the scheduled task worked.** Two complete backups within four
minutes, dumps of 227,972 and 228,027 bytes with media and `.env` alongside.

**Verification on independent hardware caught what inspection missed.** The
emergency dump was restored on a different machine and queried before anyone
relied on it. A file of the right size proves nothing.

## 4. Troubleshooting, next time

| Symptom | Run this | What it means |
|---|---|---|
| Docker Desktop error box naming a `.json` and `\x00` | Quit, then `ops\fix-docker-config.ps1` | Power cut zero-filled a config file. Never click Reset. |
| `docker` says the pipe cannot be found | `docker context ls`, then `docker context use desktop-linux` | CLI pointed at the wrong engine. |
| Engine unreachable, no Docker processes running | `Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"` | It never launched. Check Task Manager, Startup apps. |
| Machine unusable whenever Docker runs | Check `%UserProfile%\.wslconfig` has `memory=3GB` | WSL2 uncapped takes half the RAM and keeps it. |
| `docker compose ps` empty after a restart | `docker ps -a` and `docker volume ls` | `ps` hides stopped containers. Volumes present means data is safe. |
| Containers gone entirely, volumes intact | `docker compose up -d` | Someone ran `compose down`. Never do that before shutdown. |
| Backup task reports success but no folder appears | `Get-Content C:\narcos\ops\backup.log -Tail 5` | Trust the log, not `LastTaskResult`. |
| Need data off a machine where Docker is dead | `ops\copy-data-out.ps1 -To E:\rescue` | Copies backups and the WSL2 disk, no engine needed. |
| Need a backup right now | `ops\backup-now.ps1 -To E:\rescue` | Verified dump, prunes nothing, works with the app container down. |

**The one diagnosis that mattered most:** `docker ps -a` together with
`docker volume ls`. It separates "the containers are gone", which is trivial,
from "the data is gone", which is not.

## 5. Still outstanding

- The restore drill has never been run on the client's own hardware. It was
  proven here; that is not the same thing. R69 has said so since August.
- The UPS is bought, not installed. Until then, expect A and B to recur.
- Auto-login stays off by decision (D131), so recovery needs the owner to sign
  in. The card in DEPLOYMENT.md section 2b is what replaces it.
- Media has never been non-empty. When attachments start being used, the media
  archive stops being a 111-byte formality.
